# 스펙: 팀 결정 위키와 관계 그래프 (team-wiki)

- 작성: 김영균, 2026-10-31
- 상태: 초안. 팀이 도입 여부와 담당을 정한 뒤 개발을 시작합니다. 정할 것은 맨 아래 "팀이 정할 것"에 있습니다.
- 성격: 보호자가 쓰는 제품 기능이 아니라 팀 내부 도구입니다.

## 한 줄 요약

팀의 결정과 그 근거를 `docs/wiki/`에 관계와 함께 기록합니다. 스크립트가 이 기록으로 관계 그래프 페이지를 만들어 GitHub Pages에 올리므로, 팀원은 "이 결정을 왜 했고, 무엇을 근거로 했고, 전에는 무엇이었나"를 링크를 따라가며 확인할 수 있습니다.

## 누구를 위한 기능인가

**대상.** Team 10 팀원 네 명과, 팀원이 작업을 맡기는 LLM 도구입니다.

**문제가 나타나는 순간.**

- 제품 가설이 복지용구 견적 검토에서 Care Decision Assistant로 바뀌는 동안의 이유가 `PROJECT.md` Revision log, 회의록, PR 제목에 흩어져 있어, 왜 바꿨는지 다시 찾으려면 여러 문서를 열어야 합니다.
- 10/28 회의의 "음성 입력은 2단계로 미룸"처럼 회의록 표 안에 있는 결정은, 그 회의록을 기억하지 못하면 찾기 어렵습니다.
- 문서끼리 링크로 이어져 있지 않습니다. 2026-10-31 기준으로 `docs/`의 마크다운 30개에 내부 링크가 15개뿐이고, 20개 문서에는 내부 링크가 없습니다.
- LLM에게 작업을 맡길 때도 관련 문서를 사람이 매번 알려 주어야 합니다.

## 사용자가 하는 일

**결정을 찾아볼 때.** 그래프 페이지를 열어 결정을 누르면 옆 패널에 이유, 날짜, 상태, 근거 문서, 이전 결정과 이후 결정이 나옵니다. 근거 문서를 누르면 GitHub의 원문으로 이동합니다. 현재 유효한 결정만 보다가, 필요하면 "지난 결정도 보기"를 켜서 바뀐 경로를 봅니다.

**새 결정을 기록할 때.** 회의록을 올리면서 LLM에게 위키 갱신을 맡기고, 그 결과를 PR에서 사람이 확인합니다. LLM 없이 파일을 직접 써도 됩니다. CI가 끊어진 링크와 규칙 위반을 알려 줍니다.

## 구조

Karpathy의 [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 패턴을 따라 세 층으로 나눕니다.

| 층 | 위치 | 누가 어떻게 쓰나 |
|---|---|---|
| 원자료 | 지금의 `PROJECT.md`, 회의록, 설문, 스펙, WhyTree, premortem | 기존 규칙대로 작성자가 씁니다. 이 기능 때문에 원자료를 고치지 않습니다. |
| 위키 | `docs/wiki/decisions/`, `docs/wiki/problems/` | LLM이나 팀원이 쓰고 PR로 확인합니다. |
| 규칙 | `docs/wiki/SCHEMA.md` | 페이지 유형, 관계, 작성 절차를 적습니다. 특정 LLM 도구에 묶이지 않게 일반 문서로 둡니다. |

원자료를 고치지 않으므로 링크는 항상 위키 페이지에서 원자료 쪽으로 나갑니다. 고정 경로 규칙과 "다른 사람의 premortem은 고치지 않는다"는 규칙도 그대로 지켜집니다.

개별 인터뷰 기록은 일단 근거로 잇지 않습니다. 이유는 아래 "개인정보"에 있습니다.

## 온톨로지

### 노드

| 유형 | 만드는 방법 | 예 |
|---|---|---|
| 결정 | `docs/wiki/decisions/` 페이지 하나가 결정 하나 | 커뮤니티·매칭 기능 보류 |
| 문제 | `docs/wiki/problems/` 페이지 하나가 문제 하나 | 다음 단계로 넘어갈 때를 모름 |
| 근거 | 위키 페이지가 가리키는 원자료 경로에서 자동 생성 | 10/28 회의록, 설문 결과, `PROJECT.md` |
| 기능 | 위키 페이지가 가리키는 `docs/specs/` 경로에서 자동 생성 | 팀이 고른 스펙 |

근거와 기능은 페이지를 따로 만들지 않습니다. 같은 내용을 두 곳에 두지 않기 위해서입니다.

### 관계

| 관계 | 방향 | 뜻 |
|---|---|---|
| `decided_in` | 결정 → 회의록, `PROJECT.md` | 어디서 정했거나 어디에 기록됐는가 |
| `based_on` | 결정, 문제 → 근거 | 무엇을 근거로 삼았는가 |
| `addresses` | 결정 → 문제 | 어떤 문제를 다루는가 |
| `applies_to` | 결정 → 기능 | 어떤 스펙에 적용되는가 |
| `supersedes` | 새 결정 → 옛 결정 | 어떤 결정을 대체하는가 |
| `contradicts` | 결정, 문제 → 근거, 결정 | 어떤 내용과 어긋나는가 |

관계는 출처에 적혀 있거나 PR에서 사람이 확인한 것만 넣습니다.

### 페이지 형식

결정 페이지의 파일 이름은 `YYYY-MM-DD-<영문-slug>.md`이고, 파일 이름이 곧 id입니다. 일련번호를 쓰면 두 PR이 동시에 같은 번호를 쓸 수 있기 때문입니다. 아래는 10/28 회의록의 결정을 옮긴 예입니다.

```markdown
---
type: decision
title: 보호자끼리 연결하는 커뮤니티·매칭 기능 보류
date: 2026-10-28
status: confirmed
decided_in: docs/meetings/2026-10-28-minutes.md
based_on: []
addresses: []
applies_to: []
supersedes: []
contradicts: []
pr:
---

운영자가 통제하기 어렵고 사고 위험이 있어 지금은 보류합니다.
```

- 본문에는 결정의 이유를 씁니다. 결정 페이지의 본문이 비어 있으면 검사에서 걸립니다.
- `status`는 `confirmed` 또는 `tentative`입니다. 10/28의 제품 방향처럼 "확정한 것은 아닌" 결정을 구분하기 위해 둡니다.
- `pr`은 그 결정을 반영한 PR 번호이고, 없으면 비워 둡니다. 위키 페이지를 추가한 PR이 아닙니다.
- 대체 여부는 적지 않습니다. 다른 페이지의 `supersedes`가 가리키면 스크립트가 "대체됨"으로 표시합니다.
- 문제 페이지는 `docs/wiki/problems/<영문-slug>.md`이고 `type: problem`, `title`, `status`, `based_on`, `contradicts`만 씁니다.
- frontmatter 값은 한 줄 문자열과 한 줄 목록만 허용합니다. 이렇게 제한하면 YAML 라이브러리 없이 읽을 수 있습니다.

### 히스토리 규칙

- 결정 페이지의 내용은 바꾸지 않습니다. 결정이 바뀌거나 `tentative`가 확정되면 새 페이지를 만들고 `supersedes`로 이어 줍니다. 오타와 링크 수정은 고쳐도 됩니다.
- 문제 페이지는 새 근거가 나오면 고칩니다. 변경 이력은 git에 남습니다.
- 페이지 목록(index)과 날짜순 기록(log)은 저장소에 커밋하지 않고 스크립트로 만듭니다. 파일 하나를 여러 PR이 함께 고치면 충돌이 잦기 때문입니다. 시간순 변경 이력은 git과 PR 제목이 맡습니다.

## 만들 것

| 단계 | 산출물 | 완료 조건 |
|---|---|---|
| 1. 기록과 검사 | `SCHEMA.md`와 작성 절차, 초기 페이지, `scripts/wiki/` 검사 스크립트, PR에서 도는 GitHub Actions | 아래 "초기 페이지"가 올라가고 "완성 기준"의 기록·CI·운영 항목 통과 |
| 2. 그래프 | `graph.json` 생성, `docs/wiki/site/` 페이지, Pages 배포 | "완성 기준"의 그래프 항목 통과 |
| 3. 안내 | `CLAUDE.md`와 PR 템플릿의 안내 문구 | 팀이 2단계까지 쓰기로 정한 뒤 별도 PR로 반영 |

쓰임을 보고 2단계로 갈지 판단하려면 그 전에 작성 절차와 검사가 있어야 하므로, 둘을 1단계에 넣었습니다. PR은 단계별로, 규칙 문서 변경은 내용 변경과 나눠 올립니다.

1단계에서 멈추면 그래프는 없습니다. 이때는 `docs/wiki/decisions/`의 날짜순 파일 목록과 스크립트가 만드는 목록으로 봅니다.

### 기술 구성

- **스크립트:** Node.js 표준 라이브러리만 씁니다. 프로토타입이 이미 Node를 쓰고, 표준 라이브러리만 쓰면 `npm install`과 의존성 관리가 필요 없습니다. 입력은 위키 페이지이고, 출력은 `graph.json`과 검사 결과입니다.
- **그래프 화면:** 정적 HTML 한 장과 [Cytoscape.js](https://js.cytoscape.org/)입니다. 라이브러리는 버전을 고정한 파일을 저장소에 함께 둡니다.
- **배포:** `main`에 머지되면 GitHub Actions가 Pages에 올립니다. 저장소로 다시 커밋하지 않으므로 ruleset과 충돌하지 않습니다. 지금 Actions는 켜져 있고 Pages는 꺼져 있어, 관리자가 Settings에서 켜야 합니다.
- **경로 비교:** 한글 파일 이름이 있으므로 경로를 비교하기 전에 NFC로 정규화합니다. macOS에서 만든 NFD 이름 때문에 멀쩡한 링크가 끊어진 것으로 나오는 일을 막기 위해서입니다.

### CI 검사

`docs/`를 고친 PR에서 실행합니다. 원자료 파일 이름을 바꿔 위키 링크가 끊어지는 경우도 잡기 위해서입니다. 지금 ruleset에 필수 상태 검사가 없으므로, 처음에는 실패해도 머지를 막지 않고 표시만 합니다.

- 필수 필드가 없거나, 유형과 관계 이름이 정의에 없는 경우
- 가리키는 경로나 id가 없는 경우
- 결정에 `decided_in`과 `based_on`이 모두 비어 있거나 본문이 비어 있는 경우
- 문제에 `based_on`이 비어 있는 경우
- `supersedes`가 순환하는 경우
- `docs/interviews/` 경로를 가리키는 경우 (아래 "개인정보"의 결정이 바뀌면 뺍니다)

### 합성 데이터

`silicon-sampling/`은 팀 저장소에 없으므로 가리키면 경로 검사에서 걸립니다. 그래서 합성 데이터 전용 검사는 만들지 않습니다. 저장소 문서 안에서 시뮬레이션 결과를 인용한 내용을 근거로 삼지 않는다는 규칙은 `SCHEMA.md`에 적고 PR에서 확인합니다.

### 개인정보

인터뷰 가이드의 안내 문구는 응답자에게 "이름과 연락처를 뺀 내용만 팀 안에서 봅니다"라고 말합니다. 공개 저장소에 있는 인터뷰 요약이 이 약속의 범위 안인지 아직 팀이 판단하지 않았고, 그래프는 이 정보를 한곳에 모아 더 찾기 쉽게 만듭니다. 또한 C번호 노드에 문제가 이어지면, 인터뷰 대상별 페이지를 만들지 않아도 대상별 정보가 한눈에 보입니다. force push가 막혀 있어 머지한 뒤에는 히스토리에서 지울 수 없으므로, 팀이 정할 때까지 다음 기준을 따릅니다.

- 위키와 그래프에서 개별 인터뷰 기록을 잇지 않습니다. C번호 노드는 만들지 않습니다.
- 문제 페이지는 10/28 어젠다처럼 이미 묶어 정리한 문서를 근거로 삼고, 본문에는 말한 사람 수만 적습니다.
- 위키 페이지에는 실명, 연락처, C번호, 가족 사정의 세부, 직접 인용을 적지 않습니다.
- 그래프와 패널에는 위키 페이지의 내용과 원자료의 파일 이름만 씁니다. 원자료 본문은 페이지에 넣지 않고 GitHub 링크로만 연결합니다.
- 페이지에 `noindex` 메타 태그를 넣습니다. 검색 노출을 줄일 뿐 공개 여부를 바꾸지는 않습니다.

### 문제 9개

10/28 어젠다 2절의 묶음 ①～⑨를 옮기고, 그 어젠다를 `based_on`으로 잇습니다. 말한 사람 수는 어젠다의 수를 그대로 쓰고, 대표 발언과 가족 사정은 옮기지 않습니다.

어젠다가 묶음을 "초안"이라고 했고 회의록에 최종 분류가 없으므로 모두 `status: tentative`로 둡니다. 어젠다가 묻고 회의록에 답이 없는 ④ 소진과 ⑤ AI 불신(문제인가, 설계 조건인가)도 일단 문제로 두며, 회의록의 내용(⑤는 불신보다 "질문을 제대로 못 할 것 같다"는 말에 가까움)은 본문에 적습니다. 어젠다 뒤에 올라온 C9 요약은 팀이 묶음을 다시 정할 때 반영합니다.

**운영**

- [ ] 팀원 한 명이 다음 회의록을 `SCHEMA.md`의 절차로 처리한 PR이 있습니다.

## 범위에서 뺀 것

- 그래프 DB와 RDF/OWL: 문서 30개 규모에서는 frontmatter로 충분합니다. 필요해지면 `graph.json`을 옮기면 됩니다.
- 그래프 안의 전문 검색과 자연어 질문: GitHub 검색과 LLM 도구로 대신합니다.
- 날짜 슬라이더: "지난 결정도 보기"로 시작합니다.
- 그래프 화면에서 바로 편집하기: 모든 변경은 PR로만 합니다.
- PR 없이 LLM이 자동으로 커밋하는 기능: 사람이 확인하지 않은 내용이 공개 저장소에 남지 않게 합니다.
- 노션, 카카오톡 원자료 연동: 저장소에 올라온 문서만 다룹니다.
- 기존 문서의 경로 변경과 링크 일괄 삽입.
- 이미 올라간 인터뷰 요약의 처리: 동의 범위 판단과 함께 별도로 다룹니다.
- Obsidian 지원: 관계를 frontmatter의 경로로 적기 때문에 Obsidian에서 링크로 인식되지 않을 수 있습니다. 시험해 보지는 않았습니다.

## 다른 방법을 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| Obsidian만 사용 | 팀원마다 설치해야 하고 공유 URL이 없습니다. |
| Quartz | 위키 사이트로는 좋지만, [그래프 문서](https://quartz.jzhao.xyz/features/graph-view)에서 관계 종류를 구분하는 기능을 확인하지 못했고 콘텐츠를 `content/` 구조에 맞춰야 합니다. 직접 설치해 시험하지는 않았습니다. |
| GitHub Wiki | 별도 저장소라 PR 검토를 거치지 않고 그래프가 없습니다. |
| Neo4j 등 그래프 DB | 서버나 별도 도구가 필요해 7주 남은 팀 프로젝트의 유지 부담에 맞지 않습니다. |

## 위험

- **아무도 갱신하지 않음.** 가장 현실적인 실패입니다. 작성은 LLM에 맡겨 사람의 일을 검토로 줄이고, 아래의 중단 시점도 함께 정합니다.
- **제품 작업 시간 잠식.** 제 어림으로 1단계와 2단계가 각각 하루쯤 걸립니다. 측정한 값은 아닙니다. 1단계가 끝나면 2단계로 갈지 다시 판단합니다.
- **LLM이 근거를 잘못 잇거나 없는 결정을 만듦.** CI는 경로와 형식만 검사하므로 내용은 사람이 PR에서 확인해야 합니다. 작성자가 직접 머지하는 지금 규칙에서는 LLM에게 맡긴 사람이 혼자 확인하게 되므로, 아래 표에서 두 번째 확인자를 정합니다.

## 팀이 정할 것

| 정할 것 | 추천 | 이유 |
|---|---|---|
| 도입 여부와 범위 | 1단계만 먼저, 쓰임을 보고 2단계 판단 | 1단계만으로도 결정 기록과 검사는 남습니다. |
| 인터뷰 기록을 근거로 이을지 | 동의 범위를 판단할 때까지 잇지 않음 | 응답자에게 "팀 안에서 봅니다"라고 안내했습니다. 나중에 잇는 것은 쉽지만, 공개한 뒤에는 되돌리기 어렵습니다. |
| 공개 범위 | 위 개인정보 기준을 지키면 공개 Pages에 올림 | 저장소가 공개라 Pages도 공개입니다. 부담스러우면 1단계까지만 합니다. |
| 담당 | 결정 필요 | `CONTRIBUTING.md`에서는 스펙을 쓴 사람이 담당자입니다. 팀원별 역할과 맞는지 확인이 필요합니다. |
| 위키 PR의 확인자 | 결정 페이지가 든 PR은 다른 팀원 한 명이 확인한 뒤 머지 | LLM이 만든 결정이 그대로 공개 기록으로 남는 일을 막습니다. 지금 저장소 규칙보다 엄격합니다. |
| CI 실패 시 머지 차단 | 처음에는 표시만 하고 막지 않음 | 차단하면 위키를 모르는 팀원의 PR도 멈춥니다. 쓰임이 자리 잡으면 다시 판단합니다. |
| LLM 도구 | 도구를 고정하지 않고 `SCHEMA.md`로 통일 | 팀원이 쓰는 도구가 같은지 이 스펙을 쓰면서 확인하지 못했습니다. |
| 묶음 ①～⑨의 최종 분류 | 초기에는 어젠다대로 두고 다음 회의에서 정리 | 회의록에 최종 분류가 없습니다. |
| 중단 시점 | 2026-11-21까지 새 결정 페이지가 3개 미만이면 2단계로 가지 않거나 유지를 중단 | 3주면 토요일 정기 회의가 세 번 있습니다. 기록은 남겨 둡니다. |
